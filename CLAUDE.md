## Goal & Scope

Convert a KNIME `.knwf` workflow export into concise documentation.
A user uploads the file, watches AI agents work live via SSE, then downloads the doc as Word (.docx) or PDF.

### In-scope (MVP)
- Single `.knwf` file upload → async parsing → CrewAI crew → documentation
- Live agent progress streaming (SSE)
- Download as `.docx` or `.pdf`
- Basic job history per session (Postgres)

### Out of scope
- Approval workflows / sign-off chains
- Workflow versioning or diff views
- Bulk / batch processing of multiple workflows
- Team / space / hierarchy management
- Bring-your-own-model UI
- Admin-editable doc templates
- External connector integrations (KNIME Hub, GitHub, etc.)

## Architecture

```
Browser (React)
  │  upload .knwf  ──►  POST /api/doc/jobs                (FastAPI, async)
  │  SSE stream    ◄──  GET  /api/doc/jobs/{id}/events
  │  status/doc    ◄──  GET  /api/doc/jobs/{id}
  │  download      ──►  GET  /api/doc/jobs/{id}/export?format=docx|pdf
  │
FastAPI (async: asyncpg + redis.asyncio)
  │  save upload to shared volume, insert doc_jobs row
  │  enqueue  ──►  Celery task: tasks.generate_doc(job_id)   (Redis broker)
  │
Celery Worker (sync: psycopg2 + sync redis — see "Sync vs. async DB access")
  │  parse_knwf()  ──►  WorkflowGraph (pydantic)
  │  crew.kickoff(on_event=...)
  │    └── on_event, per progress event ──► INSERT doc_events (own short-lived session)
  │                                     └─► Redis PUBLISH job:{id}
  │  persist doc_documents row, update doc_jobs.status
  │
FastAPI SSE endpoint
  ├── replay doc_events from Postgres (async) for reconnect support
  └── then SUBSCRIBE job:{id} via redis.asyncio ──► text/event-stream ──► Browser EventSource
      (closes on crew_completed/error; periodic keepalive comments otherwise)
```

## Doc Template Sections

Every generated doc must contain exactly these sections, in order:

1. **Purpose** - one paragraph, what problem the workflow solves
2. **Inputs** - list of input nodes / data sources with names and types
3. **Outputs** - list of output nodes / data sinks with names and types
4. **Transformation Steps** - numbered steps, each mapping to a node or node group
5. **Notes** - caveats, known limitations, configuration tips derived from the workflow

**Rules:**

- Be concise; use bullets and numbered lists, not prose walls
- Only state facts present in the workflow XML; never invent capabilities
- No marketing filler ("powerful", "robust", "seamlessly")
- Node names come from the workflow metadata verbatim

## KNIME `.knwf` Format Notes (verified against real samples)

KNIME does not publish a formal schema for this format; the following was reverse-engineered from two real exports in `samples/` (KNIME 4.4.2) and cross-checked against scattered official docs/forum mentions. **Samples are the source of truth**, several details below (e.g. metanode structure, the `%%NNNNN%%` text escape) aren't documented anywhere and were confirmed only by inspecting real files.

- **`.knwf` is a zip file.** Top-level entry is `<Workflow Name>/workflow.knime`.
- **`workflow.knime`** is XML in KNIME's generic `NodeSettings` config format (`xmlns="http://www.knime.org/2008/09/XMLConfig"`), a key-value tree of `<entry key=".." type=".." value="..">` (scalar) and `<config key="..">...</config>` (nested) elements. Types: `xstring`, `xint`, `xboolean`, `xdouble`. `isnull="true"` means "unset."
  - `entry name` — workflow display name; often `isnull="true"` (falls back to the folder name).
  - `config annotations` → `annotation_N` → `entry text` — free-form canvas annotations (workflow-level description candidates).
  - `config nodes` → `node_<id>` → `entry id`, `entry node_settings_file` (relative path), `entry node_is_meta`, `entry node_type` (`NativeNode` | `SubNode` | `MetaNode`).
  - `config connections` → `connection_N` → `entry sourceID`, `destID`, `sourcePort`, `destPort`.
  - Arrays are encoded as a config with an `array-size` entry plus numerically-keyed entries/configs (`"0"`, `"1"`, ...).
- **Text escaping quirk:** annotation/description text embeds control characters as fixed-width `%%NNNNN` tokens (2 percent signs + 5-digit zero-padded decimal codepoint, **no closing `%%`** — tokens are concatenated directly, e.g. `%%00013%%00010` = two back-to-back tokens = CR+LF, not one wrapped token). A regex expecting a trailing `%%` misparses this: it consumes the next token's leading `%%` as its own closing delimiter, corrupting every token after the first. Must be decoded manually — it's not standard XML entity escaping (that part ElementTree already handles).
- **Per-node `settings.xml`** (for `NativeNode` and `SubNode`) has its own root config with: `model` (the actual node configuration — this is where SQL, file paths, expressions, filters live), `nodeAnnotation` (per-node canvas annotation), `customDescription`, `state`, and near the bottom: `factory` (fully-qualified Java class — the node's type identity), `node-name` (human label, e.g. "SQLite Connector"), `name` (instance display name, differs from `node-name` only if user renamed it), `ports`, `filestores`.
- **`model` settings are noisy.** Nodes with DB/type-mapping (e.g. DB Connectors) embed a `external_to_knime_mapping` / `knime_to_external_mapping` block enumerating ~30 JDBC-type conversion rules — pure boilerplate, hundreds of lines, zero documentation value. Keys ending `_Internals` (e.g. `dbTable_Internals`) are KNIME's `SettingsModelID`/`EnabledStatus` wrapper metadata, also noise. The parser skips both categories.
- **Flow variables**: a setting parameterized by a flow variable shows up as `used_variable`/`exposed_variable` string entries nested inside the relevant config (e.g. `sqlite-connection/path/used_variable = "SqlitePath"`).
- **Metanodes vs. Components (SubNodes) — structurally different:**
  - **MetaNode** (legacy): `node_settings_file` in the parent points **directly** at a nested `<subfolder>/workflow.knime` — there is no wrapping `settings.xml`. Its own name lives in that nested `workflow.knime`'s `entry name`. Ports are declared via `meta_in_ports` / `meta_out_ports` configs.
  - **SubNode** (component, current UI): `node_settings_file` points at `<subfolder>/settings.xml`, which itself has **no `factory` and no `name`/`node-name` entry** — instead it has `entry workflow-file` (= `"workflow.knime"`, sibling file in the same folder), `virtual-in-ID`/`virtual-out-ID` (ids of the internal `Component Input`/`Component Output` boundary nodes). The component's true display name must be read from that nested `workflow.knime`'s `entry name` — the containing folder name can be a truncated/sanitized variant and should not be trusted as the display name.
  - Both recurse identically otherwise: the nested `workflow.knime` has its own `nodes`/`connections`, scoped independently (child node ids are not guaranteed unique against the parent's id space).
- **Secrets**: credential fields appear as `config password` → `entry credentials` (KNIME Credential reference, not a raw password in these samples, but the field name is the reliable signal). Redact on key-name match (`password`, `credential`, `secret`, `token`, `apikey`) regardless of value, plus any string value matching an embedded-userinfo URL (`scheme://user:pass@host`).
- **Security note**: `.knwf` is untrusted user input. The parser reads zip entries via `ZipFile.read()` into memory only (never extracts to disk), avoiding zip-slip entirely, and parses XML with `defusedxml` to avoid entity-expansion/XXE issues.

## Doc Crew Notes (verified against installed crewai==1.15.22)

CrewAI's API and package layout change often — the GitHub repo has moved to a `lib/` monorepo layout since most cached docs/blog posts were written, and the docs site itself mixes a newer JSONC-based project format with the classic YAML-config format. **Everything below was confirmed by installing `crewai[anthropic]==1.15.22` in a throwaway venv and introspecting the real package** (`model_fields`, `inspect.getsource`), not by trusting search results alone.

- **Progress reporting: event bus, not `step_callback`/`task_callback`.** `Crew(step_callback=..., task_callback=...)` exist but have long-standing "not firing" bug reports upstream. `crewai.events` (import path confirmed working) is the actively maintained mechanism and gives finer granularity than the two callbacks combined: `AgentExecutionStartedEvent`, `LLMCallStartedEvent` (→ "thinking"), `ToolUsageStartedEvent`, `TaskCompletedEvent`/`TaskFailedEvent`, `CrewKickoffCompletedEvent`/`CrewKickoffFailedEvent`. Subclass `BaseEventListener`, implement `setup_listeners(self, bus)`, register with `@bus.on(EventType)`.
- **`event.agent_role` is unreliable — verified empirically, not documented.** Several event types (`AgentExecutionStartedEvent`, `TaskCompletedEvent`, ...) declare an `agent_role: str | None` field that is simply `None` in practice for at least this version; a real end-to-end run showed every progress line printing `None started working` until fixed. The nested `event.agent` (a real `BaseAgent`) or `event.task.agent` is reliable — `app/crew/events.py`'s `_agent_role()` tries `agent_role` first, then falls back through `agent.role` / `task.agent.role`.
- **Scoped listener registration**: `crewai_event_bus.scoped_handlers()` (context manager) swaps out *all* global handlers on enter and restores them on exit — it's a full swap, not a per-run filter, so it's only safe when one crew runs per process at a time. Celery's default prefork pool gives each concurrent task its own OS process anyway, so this is fine as-is; **if the worker is ever switched to a threaded/eventlet/gevent pool, this assumption breaks and needs revisiting.**
- **`Agent(config=dict, llm=...)` / `Task(config=dict, agent=..., context=[...])` both work directly** — no need for the `@CrewBase` decorator/class-based project scaffolding (which assumes a `crewai create crew`-style directory convention). Plain `yaml.safe_load()` + explicit `Agent(config=...)`/`Task(config=...)` calls are simpler and more transparent for this project's custom layout. Task `context` must be a list of real `Task` objects, not name strings — our YAML uses name-string lists as a project convention and `app/crew/crew.py` resolves them by building tasks in declaration order.
- **YAML gotcha**: `>` (folded, "clip") keeps one trailing newline, which leaked into `Agent.role` (`"KNIME Workflow Analyst\n"`) and broke printed progress messages. Use `>-` (folded, "strip") for role/goal/backstory/description fields.
- **`temperature` is rejected outright by Claude Sonnet 5** — a live HTTP 400 (`` `temperature` is deprecated for this model ``), not a docs-staleness issue. `app/crew/llm.py` passes `max_tokens` only.
- **`crewai[anthropic]` extra is required** for the native Anthropic provider (`LLM(model="anthropic/claude-sonnet-5", ...)` raises `ImportError` otherwise, pointing at the exact extra). Installing plain `crewai` (no extras) does **not** pull in `crewai-tools`/`embedchain` in this version — unlike the unpinned `crewai==0.80.0` attempt in Stage 0, `pip install crewai[anthropic]` resolves quickly. `requirements-ai.txt` intentionally avoids `crewai[tools]`/`crewai-tools` since this MVP's agents use no tools.

## API & Worker Wiring Notes (Stage 3)

- **Sync vs. async DB access — deliberate split, not an oversight.** FastAPI routes use the async engine (`app/db/session.py`, asyncpg). The Celery worker (`app/services/doc_pipeline.py`) uses a **separate sync engine** (`app/db/sync_session.py`, psycopg2, `settings.sync_database_url` — derived from `database_url` by swapping the driver, not a new env var) against the same database and the same `app/models/` definitions. Reason: `crew.kickoff()` is a blocking call that fires progress events synchronously mid-call; there is no running event loop to await into from inside those callbacks, so the whole pipeline stays synchronous rather than mixing in `asyncio.run()`.
- **`crew.kickoff()` uses background threads internally — verified by a live production bug, not by reading crewai's source.** A real end-to-end run threw `sqlalchemy.exc.ResourceClosedError: This transaction is closed` partway through, from a single `Session` object being shared across the whole `generate_doc` task and reused inside the `on_event` callback. Root cause: crewai's agent execution loop runs via `asyncio.to_thread()` (seen in the Stage 2 introspection of `crewai/flow/runtime`), so `on_event` is not guaranteed to run on the same thread that created the session — and SQLAlchemy `Session` objects are not thread-safe for concurrent use. **Fix: every DB write in `doc_pipeline.py` opens its own short-lived session** (`with SyncSessionLocal() as session: ...`, one per event/status write) instead of threading one session through the task. This is also just the standard SQLAlchemy "session per unit of work" pattern — the thread-safety bug was a symptom of not following it, not a novel problem. An earlier, subtler version of the same class of bug (`PendingRollbackError`, from a job row being deleted concurrently by a test's `TRUNCATE` while the worker still held a stale reference) was fixed the same way, before the thread-safety root cause was fully understood.
- **`crewai==1.15.22` forces several pins in `requirements.txt`** once it's installed alongside FastAPI/pydantic — found by iterating `pip install --dry-run` locally (much faster than rebuilding Docker per attempt) rather than guessing: `httpx==0.28.1` (crewai needs `~=0.28.1`), `pydantic==2.12.0` (crewai needs `>=2.11.9,<2.13`), `pydantic-settings==2.14.2` (crewai needs `>=2.14.2`), `uvicorn==0.32.0` (crewai's `mcp` dependency needs `>=0.31.1`). None of these came from crewai's own docs — pip's resolver error messages were the only source.
- **`docker compose build ... | tail -N` swallows the real exit code** — `tail`'s exit code is what a pipeline reports, not `docker compose build`'s. A build that actually failed (the httpx conflict above) was reported as "completed successfully" this way. Use `set -o pipefail`, or redirect to a file and check `$?` separately, when a build's own success/failure matters.
- **`samples/` must be volume-mounted into the `api` container** (`./samples:/samples:ro` in docker-compose.yml) for `tests/test_parser.py` to find its fixtures when run via `docker compose exec api pytest` — it worked when run against a local venv (Stage 1/2) purely because the real filesystem path existed there; the container has no such path without an explicit mount.
- **pytest-asyncio + a module-level async engine needs a session-scoped event loop.** `app/db/session.py`'s `engine` is created once at import time, binding its asyncpg connections to whatever event loop exists then. pytest-asyncio's default per-test-function event loop causes every test after the first to fail with `Future attached to a different loop`. Fixed with a session-scoped `event_loop` fixture override in `tests/conftest.py` (pytest-asyncio 0.24.0 still supports this; it's deprecated for future versions, but works cleanly at the pinned version).

## Export Notes (Stage 4)

- **WeasyPrint's system dependencies shrank a lot in recent versions — verified against the current stable docs, not assumed from older Stack-Overflow-era advice.** Pre-v53 WeasyPrint needed cairo + GDK-Pixbuf + GObject introspection (a long, easy-to-get-wrong apt list). Current WeasyPrint (`70.0`, pinned) renders PDFs itself via `pydyf` and only needs Pango: `libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz-subset0` (from WeasyPrint's own current install docs). `fonts-liberation` was added on top so the PDF actually has a real font to rasterize with — WeasyPrint needs the font file present in the *generating* container, unlike DOCX (see next point).
- **DOCX fonts vs. PDF fonts are not the same kind of dependency.** A `.docx` only records a font *name* in its XML; the *viewer's* machine (Word/LibreOffice, wherever the file is eventually opened) supplies the actual glyphs, so `app/exporters/style.py` uses `"Calibri"` for DOCX with zero concern for what's installed in the Docker image. A PDF is rasterized once, at generation time, by whatever's in the container — so the PDF CSS uses `"Liberation Sans"` (the family `fonts-liberation` actually installs, metrically compatible with Arial) instead. "Consistent styling between formats" therefore means the same accent color / hierarchy / structure, not literally the same font file, which isn't achievable (or necessary) across the two mechanisms.
- **No markdown/HTML importer exists for python-docx.** The DOCX exporter (`app/exporters/docx_exporter.py`) walks markdown-it-py's `SyntaxTreeNode` tree (verified structure via direct introspection — same approach as the other "don't trust docs, run it" notes in this file) and maps each node type onto a python-docx call by hand: headings → `add_heading`, list items → the built-in `"List Bullet"`/`"List Number"` styles (confirmed present in python-docx's default template by listing `document.styles`; depth >1 uses the `"... 2"`/`"... 3"` suffixed variants), tables → `add_table` + manual `w:shd` XML for header-row shading (no high-level python-docx API for cell background color), inline bold/italic/code → recursive run-building from the `inline` node's children. The PDF path is much simpler by comparison — markdown-it-py renders straight to HTML, WeasyPrint takes it from there.
- **Real bug caught only by end-to-end testing with two different real docs, not by unit-testing one:** the Documentation Writer's task only asks for the five `##` sections, but one live-generated document included its own `# Workflow Name — Doc` title line and another didn't. Since both exporters always render their own title/date/disclaimer header block, the one with a title line produced a visibly duplicated heading (`Title` style "Retry Database Connection" immediately followed by a `Heading 1` "Retry Database Connection — Doc"). Fixed defensively at the exporter layer (`markdown_render.strip_leading_h1`), not by trying to make prompt-engineering eliminate LLM non-determinism.
- **Local iteration without Docker**: python-docx and markdown-it-py are pure Python, so the DOCX path was verified in a throwaway local venv against real generated documentation markdown before ever rebuilding the image. WeasyPrint needed Pango too, which happened to already be on this machine via Homebrew (`brew list pango`), so the PDF path got the same fast local iteration — not something to assume is always available; the container is the authoritative environment either way.
- **`GET /api/doc/jobs/{id}/export?format=docx|pdf`**: 404 if the job doesn't exist, 409 if it exists but isn't `COMPLETED` yet, 422 (automatic, from the `Literal["docx","pdf"]` type) for any other `format` value. Filename comes from `job.workflow_name` (sanitized), sent via both a plain `Content-Disposition: filename="..."` and an RFC 5987 `filename*=UTF-8''...` (percent-encoded) parameter for broader client compatibility with non-ASCII names.

## Frontend Notes (Stage 5)

- **Design system, chosen before any component code**: `ink`/`paper`/`mist`/`line`/`accent`/`amber`/`moss`/`rust` tokens in `tailwind.config.js`. `accent` (`#1F4E79`) deliberately reuses the DOCX/PDF exporters' `ACCENT_HEX` (`app/exporters/style.py`) and `rust` (`#B00020`) reuses their disclaimer red, so the live tool and the document it produces read as one family. Node names/IDs/filenames are set in `font-mono` throughout (matches the exporters' `Consolas` treatment for `code_inline`) to visually mark "this came verbatim from the workflow" vs. the AI's own prose.
- **No router, no state library.** Two screens with no shared nested state — `App.tsx` is a ~30-line switch on `window.location.pathname` with a `history.pushState` `navigate()` helper. `react-router` would be pure overhead. Same reasoning kept dependencies to exactly two additions beyond the Stage 0 scaffold: `react-markdown` + `remark-gfm` (doc rendering) and `lucide-react` (icons) — no `@tailwindcss/typography`, hand-written `.doc-markdown` CSS in `index.css` instead, since it's a handful of elements and another dependency wasn't worth it for that.
- **Vite's dev proxy, not CORS, is what makes the browser calls work.** `vite.config.ts` already proxied `/api` → `http://api:8000` (the Docker-internal service name) since Stage 0; the frontend code was written to call relative paths (`/api/doc/...`) throughout (`src/api.ts`) rather than an absolute `VITE_API_URL`, so the browser only ever talks to one origin. This also means `EventSource` "just works" through the proxy with zero special-casing — SSE is plain HTTP, and Vite's proxy streams it through without buffering.
- **Real bug found only by watching a live run, not by reading the code**: `crew_completed`/`error` progress events are published from *inside* `run_doc_crew()` (CrewAI's own event bus fires on `CrewKickoffCompletedEvent`), which returns to `doc_pipeline.py` *before* the pipeline writes the `DocDocument` row and sets `job.status = COMPLETED` (`doc_pipeline.py:96-101`). A first implementation refetched the job exactly once when the terminal SSE event arrived — by the time this shipped and a real run of the larger `Format Multiple Excel Sheets.knwf` sample was watched end-to-end in the browser, the fetch reliably landed in that gap and the status pill stuck on "Running" forever (the SSE stream had already closed, so nothing would ever trigger another refetch). Fixed in `JobPage.tsx`'s `waitForTerminalStatus()`: on a terminal event, poll `GET /jobs/{id}` every 400ms (up to 25 attempts) until the job's own status is actually `completed`/`failed`, instead of trusting the event's timing. A smaller version of the same fix — refetching on *every* event, not just terminal ones — was also needed so the status pill tracks `queued → parsing → running` instead of jumping straight from "Queued" to a terminal state.
- **Backend event messages already read as full sentences** (e.g. `"KNIME Workflow Analyst started working"`), but the UI also shows the agent name as its own line above each entry — printing both verbatim reads like a stutter. `ProgressTimeline.tsx`'s `messageWithoutAgentPrefix()` strips a leading duplicate of the agent name for *display only*; the underlying event data passed through the API is untouched.
- **No backend retry endpoint exists** (a job is a one-shot record; there's nowhere durable to re-fetch original upload bytes from, since uploads live in a server-side volume keyed by job id, not by content). `lib/retryCache.ts` keeps an in-memory `Map<jobId, File>` populated at upload time, scoped to the browser tab: if a job fails and its file is still in that map, the failed-state UI offers "Retry with the same file" (resubmits via `POST /jobs` and navigates to the new job id); otherwise — e.g. the job page was reached via a bookmarked/shared link or a page reload — it falls back to "Upload a new file" pointing home. Verified both paths against a real failing upload (a deliberately corrupt `.knwf` that fails `parse_knwf`'s zip check with `BadZipFile: File is not a zip file`, surfaced verbatim as `job.error`): retry resubmitted and failed identically (proving the resubmit path works), and a fresh page load of the same failed job correctly showed "Upload a new file" instead.
- **Verified in a real browser (Chrome via the `claude-in-chrome` extension), not just by reading component code**: full upload → live SSE timeline → completed doc render → both downloads, for both the small and large real samples in `samples/`; the invalid-extension and corrupt-file error paths; keyboard-only navigation (Tab reaches the dropzone first, then job rows, each with a visible focus ring; Enter activates a focused job row); and layout at a 390px mobile width (no horizontal scroll, buttons wrap, truncated job names still show status/time). `tsc --noEmit` and `vite build` both pass clean.

## Failure Handling Hardening (Stage 7)

- **Real bug found only by testing the *largest* sample, not the small one**: a live run against `samples/Format Multiple Excel Sheets.knwf` came back with its entire document wrapped in a single ` ```markdown ` fence — as if the Documentation Writer were demonstrating markdown syntax rather than emitting it. Left in, every heading/list/table would render as one inert preformatted code block in both exporters and the in-browser preview, since none of them treat a fenced code block's contents as markdown to parse further. Fixed defensively (same pattern as Stage 4's `strip_leading_h1`, not by trying to prompt-engineer away LLM non-determinism): `app/exporters/markdown_render.py:strip_wrapping_code_fence()` unwraps a fence only when it spans the *entire* document (so a legitimate code block the doc includes partway through, e.g. a config snippet in Notes, is untouched), composed with `strip_leading_h1` via a new `clean_markdown()` used by both exporters; mirrored client-side in `frontend/src/lib/markdown.ts` (`stripWrappingCodeFence`/`cleanMarkdown`) since the in-browser preview renders the same raw `job.markdown`. Verified against the actual captured buggy output, both as a unit test (`tests/test_markdown_render.py`) and by re-exporting the real stored job and confirming DOCX headings/lists rendered properly instead of one code block.
- **Size guard (`app/parser/budget.py`) — real samples never trigger it.** Both samples in `samples/` serialize to just 10KB/21KB of JSON (the parser's existing noise-stripping already does most of the work — see "model settings are noisy" above), nowhere near the `MAX_JSON_CHARS = 60_000` budget. This is a forward-looking guard for larger workflows, verified with a synthetic oversized `WorkflowGraph` instead (`tests/test_budget.py`). That synthetic test caught a real scaling bug in the first implementation: trimming each node's `settings` to a handful of short values isn't enough on its own when the workflow has *many* nodes — 50 nodes at the first trim level still serialized to 67KB, over budget, because per-node overhead (name/factory/connections/etc., never trimmed) adds up independently of `settings` size. Fixed with progressively stricter `(max_items, max_str_len)` levels, each re-applied from every node's *original* untouched settings (not the previous level's already-trimmed result, which would compound inaccurately) until the graph fits or levels run out. When trimming happens, a fixed note is inserted programmatically as the first bullet under `## Notes` (`doc_pipeline.py:_insert_note()`) — not left to the LLM to notice and mention, since it has no way to know what was cut before it ever sees the JSON.
- **A missing `ANTHROPIC_API_KEY` is checked before any work starts**, not left to surface from the crew's first LLM call. Failing fast here matters more than it sounds: without this check, a misconfigured deployment would only find out ~240 seconds later (Celery's `soft_time_limit`) rather than immediately. Verified with a unit test (`tests/test_doc_pipeline.py::test_generate_doc_fails_fast_without_api_key`) — deterministic and free, no live API call needed for this specific case.
- **Real bug found only by actually stopping the Redis container, not by reading the code**: a `try/except` wrapped around `generate_doc.delay(...)` (to fail a job cleanly if the broker is unreachable) looked correct but did nothing useful in practice — with `redis` stopped, the call didn't raise for **~20 seconds**, and worse, since `create_job` is an `async def` FastAPI route calling a *synchronous* blocking function directly, that ~20s also froze the entire single-process API for every other concurrent request, confirmed by firing a health-check request at the same time and watching it queue behind the stuck one. The root cause wasn't a slow TCP connection (an explicit `socket_connect_timeout` doesn't touch this) — it was Docker's embedded DNS no longer resolving the `redis` hostname once its container stopped, combined with kombu's own connection-retry logic retrying that failing resolution several times before giving up. **Fix**: `create_job` now runs the enqueue call via `asyncio.wait_for(asyncio.to_thread(generate_doc.delay, ...), timeout=5)` — the thread offload stops one stuck request from blocking every other request on the same process, and `wait_for` puts a hard wall-clock bound on the response regardless of *why* the underlying call is slow (DNS, TCP, retries, or anything else). Explicit `socket_connect_timeout`/`socket_timeout` were still added to all three Redis client construction points (`celery_app.py`'s `broker_transport_options`, the sync publisher in `doc_pipeline.py`, the async subscriber in `routes/doc.py`) as defense-in-depth against the *TCP-level* version of this problem, plus `task_publish_retry=False` to avoid stacking Celery's own publish-retry delay on top — but none of those alone fixed the observed hang; the `wait_for` wrapper is what actually did. Re-verified live after the fix: enqueue-while-down now fails in ~7s with `"Could not queue the job — the background worker is unavailable. Try again shortly."`, and a concurrent health-check request completed in 0.63s, confirming the server no longer freezes.
- **The SSE endpoint's Redis subscribe (`redis.asyncio`), tested the same way, turned out not to have this problem** — with Redis stopped, `pubsub.subscribe()` raised almost immediately (~0.2s), unlike the sync kombu client used for Celery publishing. The `except Exception` block added around the subscribe/read loop (emitting a real `"error"` SSE event — `"Lost connection to the live progress stream..."` — instead of letting the connection just silently drop) turned out to matter more than the socket-timeout addition for this specific path, but both are in place. Re-verified afterward that normal SSE streaming (real crew run, real keepalive comments during LLM think-time) still works correctly with the added `socket_timeout=5` — it doesn't fight with the pubsub `get_message(timeout=15)` keepalive polling.
- **Secrets-in-logs review**: `app/services/doc_pipeline.py:_sanitize_error()` redacts anything shaped like an API key (`sk-[A-Za-z0-9_-]{10,}`) and caps error text at 500 characters, applied to *both* what's logged and what's stored in `job.error` (visible verbatim in the UI) — some LLM provider client libraries echo the request's own key back in an auth error's message, and `logger.exception`'s automatic traceback formatting would otherwise print that raw message straight into the worker's logs regardless of what the log call's own message argument said. Also found and fixed: `GET /api/v1/health` returned raw `str(exc)` for DB/Redis connectivity failures on an *unauthenticated* endpoint — a driver-level connection error can echo back the DSN (including credentials); changed to `type(exc).__name__` only.
- **Unused code removed**: `EventOut` (a pydantic schema in `app/schemas/doc.py` that was never actually used — the SSE endpoint builds raw dicts via `serialize_event` instead) and `secret_key`/`SECRET_KEY` (a config field and env var left over from initial scaffolding, read nowhere in the codebase — removed from `config.py`, `.env`, and `.env.example`).
- **Missing type hints filled in** across `app/parser/xmlconfig.py` (added a `JsonValue` recursive type alias for the dict/list/scalar shape `config_to_value()` produces, used throughout that module instead of bare untyped params), `app/parser/knwf.py`, `app/exporters/docx_exporter.py` (real `python-docx`/`markdown-it-py` types — `Paragraph`, `Run`, `_Cell`, `SyntaxTreeNode` — instead of untyped params), `app/exporters/style.py`, and `app/crew/events.py`/`crew.py` (a `_RoleBearingEvent` union type for `_agent_role()`, `LLM` for `_build_agents()`). `crew/events.py`'s `bus: object` param is deliberately not typed as crewai's real `CrewAIEventsBus` class — that class lives in a private submodule (`crewai.events.event_bus`) not re-exported publicly, and this project already avoids importing crewai internals directly (see "Doc Crew Notes" above).

## Conventions

- **Type hints everywhere** — no `Any` without a comment explaining why
- **Pydantic v2 schemas** — separate `schemas/` from `models/` (ORM)
- **Small modules** — each file has one primary concern; if it exceeds ~150 lines, split it
- **Async FastAPI** — all route handlers and DB calls are `async`
- **Celery tasks are thin** — business logic lives in `services/`, tasks just orchestrate
- **Never log secrets** — API keys, tokens, passwords must not appear in any log line
- **Tests** — `pytest` with `pytest-asyncio`; cover the KNIME parser and main API routes
- **Migrations** — every schema change gets an Alembic migration; never `create_all()` in production
- **Imports** — absolute imports from `app.*` inside the backend package
